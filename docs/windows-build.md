# Windows Build (x86_64-pc-windows-gnu)

This is the native Windows port of a recompiled title, not an emulator. The
first milestone is compile and boot: the executable links, `SDL3.dll` and the
Vulkan loader are found, and the SDL3 window opens. No game data, keys or
other proprietary assets belong in the repository; the user supplies the
RomFS image and save data at run time.

Linux behavior is unchanged. The Windows-specific code is limited to the
generated program's opt-in subsystem attribute, the Vulkan backend's DLL
diagnostics and path base, and the packaging script.

## Prerequisites

- Rust stable with the mingw target:

  ```
  rustup target add x86_64-pc-windows-gnu
  ```

- mingw-w64 on `PATH`. On Linux this is `x86_64-w64-mingw32-gcc` (for example
  `mingw-w64` on Arch, `mingw-w64` on Debian/Ubuntu, or the Nix dev shell).
  On Windows, build from an MSYS2 **MINGW64** shell, where the compiler is
  `x86_64-w64-mingw32-gcc` or `gcc`.

- SDL3 3.4.18's mingw development package. The `sdl3` crate 0.20 is built
  against SDL 3.4.18:

  ```
  https://github.com/libsdl-org/SDL/releases/tag/release-3.4.18
  asset: SDL3-devel-3.4.18-mingw.zip
  ```

  Unpack it anywhere; the needed layout is:

  ```
  SDL3-3.4.18/
    x86_64-w64-mingw32/
      include/SDL3/SDL.h
      lib/libSDL3.dll.a     <- import library the link step needs
      bin/SDL3.dll          <- runtime DLL staged beside the game
  ```

  `sdl3-sys` emits `-lSDL3`; it needs the import library at link time and the
  DLL at run time. Nothing from the package is committed to this repository.

- Vulkan 1.3 capable GPU drivers. Windows installs `vulkan-1.dll` in
  `C:\Windows\System32` with the driver. The Vulkan loader has no import
  library requirement here because `ash` (and SDL) load it dynamically with
  `LoadLibrary`, not at link time. For an offline bundle, the Vulkan SDK's
  `Bin\vulkan-1.dll` can be copied beside the executable.

- libvpx for the VP9 cutscene decoder. The game loads it at runtime, not at
  link time. MSYS2's `mingw-w64-x86_64-libvpx` provides
  `/mingw64/bin/libvpx-1.dll`; copy it beside the executable (or set
  `LIBVPX_DLL=<path>` for `scripts/build-windows-gnu.sh`). Without it, NVDEC
  has no decoder and the castle/intro movies render transparent.

## Build the game binary

1. Generate the title with the Vulkan backend (`[runtime] graphics = "vulkan"`
   in `title.toml`):

   ```
   cargo run -p recomp-cli -- run \
     --module <lifted module.json> \
     --config <title.toml> \
     --provenance <provenance.toml> \
     --out-dir out/<title>
   ```

2. Build and stage the Windows binary:

   ```
   scripts/build-windows-gnu.sh \
     --project-dir out/<title> \
     --sdl3-dir /path/to/SDL3-3.4.18/x86_64-w64-mingw32
   ```

   The script adds the SDL3 import-library directory to the link search,
   builds for `x86_64-pc-windows-gnu`, and stages the result in
   `out/<title>/dist/windows/`. `--release` is the default. `--debug` builds
   with a console window, and `--gui` forces the Windows GUI subsystem for a
   debug build too. `SDL3_DIR` and `VULKAN_SDK` are also read. On Windows run
   the script from an MSYS2 **MINGW64** shell or Git Bash (`/c/...` paths).

3. The staged directory must look like this:

   ```
   dist/windows/
     <title>.exe
     SDL3.dll              <- required; same directory as the executable
     vulkan-1.dll          <- optional; otherwise System32's loader is used
     ...                   <- RomFS image / assets as configured
   ```

   Run the executable from any directory. The release build is a GUI program
   (no console window); its logs are not visible. Use a `--debug` build while
   diagnosing startup, or run with `RECOMP_VULKAN=0` to fall back to the
   recording backend and a console-only build path.

## Windows subsystem

The generated `main.rs` starts with:

```rust
#![cfg_attr(all(windows, feature = "windows-subsystem"), windows_subsystem = "windows")]
```

`windows-subsystem` is an opt-in Cargo feature declared by the generated
package, so:

- `cargo build` and `--debug` builds keep stdout/stderr (console subsystem),
- the release packaging build passes `--features windows-subsystem` and gets
  a GUI executable with no console window beside the game,
- non-Windows targets ignore the attribute.

This is the equivalent of adding `#![windows_subsystem = "windows"]` for
release builds without taking away console output from debug builds. The
script passes the feature only for release (or with `--gui`). A project
generated by an older pipeline has no feature; regenerate it or the release
binary keeps a console window.

## Paths, assets and saves

- A relative path in `RECOMP_VULKAN_DUMP` or `RECOMP_VULKAN_CAPTURE` is
  resolved against `RECOMP_BASE_DIR` when set, and on Windows against the
  executable's directory. Elsewhere the working directory is kept.
  `scripts/build-windows-gnu.sh` does not set `RECOMP_BASE_DIR`; start the
  game from `dist/windows` or set it explicitly if your launcher changes the
  working directory.
- The generated `main` resolves a relative `[runtime.ipc] romfs_image` (and
  the default script path) the same way, so a shortcut or Explorer launch
  does not depend on the shell's current directory.
- Save data goes to `RECOMP_SAVE_DIR` when set, otherwise to a `save/`
  directory beside the RomFS image. Both are ordinary Windows paths; no
  `/home`, `/dev` or `/proc` path is assumed by the host backend.
- The write watch uses `MEM_WRITE_WATCH` and `GetWriteWatch` on the guest
  reservation. Vertex ranges and regular textures are checked this way; the
  nine small 3D colour LUTs rewritten during a door fade are hashed directly
  because the page watch is unreliable for those pool textures. The profiler
  remains Linux-only.

## Window, input, audio

- SDL is initialized, and the window and Vulkan surface are created, on the
  backend's `recomp-window` thread. SDL records the thread that initializes
  video as its video/event thread; on Windows the Win32 message pump runs on
  the thread that created the window, which is the same thread. Closing the
  window exits the process.
- F1 opens the menu, F11 toggles fullscreen. Fullscreen is SDL's borderless
  desktop fullscreen; resizing recreates the swapchain. Mailbox or immediate
  present is used when the driver offers it, else FIFO.
- Gamepads use SDL's gamepad mappings; `RECOMP_PAD_LAYOUT=positional` maps by
  position instead of label. Keyboard mappings are in `docs/DEVELOPMENT.md`.
- Audio opens the default playback device at 48 kHz stereo through SDL's
  WASAPI driver. If no device opens, the title runs silently.

## Shader warm-up and pipeline cache

The game ships its Maxwell shader library in `init.data` asset `0063.dat`.
`crates/recomp-gfx/examples/translate_library.rs` extracts the 5,145 aligned
shader blocks and translates them to SPIR-V offline; 4,671 unique shaders
succeed. The resulting `shader-pack.bin` is loaded in `Gpu::new` before the
first frame, and a matching `(code hash, attribute types)` hit skips live
Maxwell translation. The loader keeps the file open, builds a small offset
index, and parses an entry on first use: startup is about 12 ms and 5 MB
instead of 212-224 ms and ~320 MB. A 30-second title test logged one 1.3 ms
fallback translation.

The code hash covers a program's first 0x200 bytes, and material variants
often share them: LM3's pack has 171 keys shared by 500 entries. Such a key
is ambiguous, so its lookup misses and the program the game uses is
translated live (the loader logs the count). Taking one of the variants ran
another material's code. Hellen Gravely's pendant in the lobby read leftover
constant words as its colour and flickered between red and yellow.

The driver pipeline cache remains GPU/driver specific. `pipeline-cache.bin`
is loaded at startup, saved every 64 new pipelines, and saved again by the
renderer destructor on a normal window close. The local LLPC 26.10.1 cache
is about 8.59 MB; a cold late-game load created pipelines in 143-180 ms,
while the warmed cache created none over 10 ms.

For another GPU, `tools/shader-precompile` is a standalone Vulkan program
that reads `shader-spv/manifest.tsv` and the `.spv` files and builds a local
`pipeline-cache.bin` **without launching the game**. `precompile-shaders.bat`
runs it one shader per process so a driver crash on an invalid library
variant is recorded in `bad-shaders.txt` instead of aborting the whole
build. Those few variants fall back to live translation if the game uses
them.

`RECOMP_PIPELINE_CACHE=<file>` chooses another cache path; an empty value
disables the cache. `RECOMP_SHADER_PACK=<file>` chooses another pack; an
empty value disables it. `RECOMP_SLOW_PIPELINES=<ms>` logs any shader
translation or pipeline creation at or above that duration. Keep the cache
and pack with the local game data and do not publish them.

## Status

The native Windows port builds and boots. `recomp-runtime` has the Windows
fault handler and guest-memory mapping, `recomp-services` uses the portable
`file_at` helpers for RomFS/save I/O, and the SDL3/Vulkan backend has the
Windows path and DLL diagnostics. The write watch is now available on
Windows through `GetWriteWatch`; the profiler remains Linux-only. The rebuilt
package includes the 32-texture-binding fix for the AMDVLK title-screen crash
described in Troubleshooting. VP9 cutscenes load
`libvpx-1.dll` at runtime, and `game.rhai` selects 180 FPS instead of the
game's 30 FPS default.

## Troubleshooting

- `cannot find -lSDL3`: `--sdl3-dir`/`SDL3_DIR` does not point at the
  `x86_64-w64-mingw32` directory containing `lib/libSDL3.dll.a`, or an
  existing `RUSTFLAGS` was overwritten. The script appends
  `-L native=<dir>`.
- `SDL3.dll was not found`: copy `bin/SDL3.dll` next to the `.exe` (the
  script does this). Do not rely on the current directory.
- `vulkan-1.dll was not found` or `VK_ERROR_INCOMPATIBLE_DRIVER`: install a
  Vulkan 1.3 driver; for an offline machine copy the Vulkan SDK's
  `Bin/vulkan-1.dll` beside the executable.
- No console output from the release binary: expected (GUI subsystem). Use a
  debug build or `--debug` while debugging.
- Paths with spaces: use `CARGO_ENCODED_RUSTFLAGS` or a path without spaces;
  `RUSTFLAGS` is whitespace-split by Cargo.
- Access violation in `amdvlk64.dll` while creating a graphics pipeline:
  the build's descriptor set layout had fewer texture bindings than the
  shader samples. LM3's title-screen fragment shader `0x4012a3030` uses 17
  texture bindings (binding 48); the current source declares 32
  (`TEXTURE_BINDINGS` in `recomp-gfx-vulkan/src/gpu.rs`) and
  `pipeline()` skips an out-of-range pipeline before the driver sees it.
  Rebuild the Windows package after updating the source. For a pre-fix
  binary, `RECOMP_VULKAN_SKIP_FS=0x4012a3030` avoids the crash but leaves
  the distant grass/terrain black.

## Fast native-TLS build

Rust's `thread_local!` uses `TlsGetValue` on Windows. The lifted code enters a
block on every guest function and calls the scheduler from hot paths, so that
wrapper made the Wine test run at about 42 FPS even with optimized chunks.
Building with native Windows TLS (`#[thread_local]`) removes the wrapper.

The generated code calls `recomp_abi::enter_block`/`backedge` inline, so this
option rebuilds the 506 chunks. Pass `--fast-tls` to
`scripts/build-windows-gnu.sh` (it sets `RUSTC_BOOTSTRAP=1` and
`--cfg recomp_fast_tls`) or set them in the environment. Without the flag the
ordinary stable `thread_local!` path still builds and runs.

Measured on the Wine/LM3 lobby harness with optimized chunks:

```text
stable thread_local!     ~42 FPS
native TLS               ~166 FPS
```

The Linux build already uses ELF TLS and is unaffected.
